### 2.4 构建约束

- `Dockerfile:1` 使用 `node:lts-alpine`，未锁定 Node major。
- `Dockerfile:6` 使用 `yarn`；仓库实际只有 `web/desktop/bun.lock`，锁文件未参与构建。
- 前端无单测、无 E2E；`package.json:5-10` 只有 `dev`、`build`、`preview`、`lint`。
- 前端产物由 `server/internal/api/http/dist` 嵌入 Go 二进制，构建链改动必须保持 `make build_fe` 的输出路径不变（`docs/20-功能/05-构建与部署.md`）。

### 2.5 Arco 维护状态

- 官方 `@arco-design/web-vue` 在 2026-04 发布 2.58.0、2026-10 发布 2.59.0，并非停止维护；但 2024-2025 年发版间隔较长。
- 社区 fork `@uno-arco/web-vue` 在 2026-11 发布 2.60.2，GitHub Issue #3566 记录了社区接手的讨论。
- 选择官方 2.59.0 的理由：文档、图标、Resolver、TS 类型与 npm 包名统一；社区 fork 的包名与文档生态不同，后续切回官方有额外成本。风险是官方后续发版节奏可能慢于 fork，需在验收中记录锁版本并保留升级观察项。

## 3. 候选方案

### 3.1 UI 组件库

| 候选 | 结论 | 理由 |
| --- | --- | --- |
| 保留 Element Plus 2.14.8 | 排除 | 与用户明确的 Arco 口径不一致；Element Plus 自身仍在更新，但本轮目标是切换组件体系 |
| `@arco-design/web-vue` 2.59.0 | **采用** | 官方包、文档与 TS 类型完整；2026-10 仍有发布；Resolver 与图标体系可直接接入 |
| `@uno-arco/web-vue` 2.60.2 | 不采用 | 社区 fork 更新更快，但包名、文档、Resolver 与长期维护主体不同；切换成本高于本轮收益 |

### 3.2 构建链版本口径

| 候选 | 结论 | 理由 |
| --- | --- | --- |
| 保持 Vite 4 / Pinia 2 / Router 4 | 排除 | 与“技术栈升级到最新推荐版”的目标不符 |
| Vite 7 + Pinia 3 + Router 4 | 排除 | 稳定但非最新推荐版；用户已明确要求同步升级 |
| Vite 8.3.8 + Pinia 4.1.0 + Router 5.5.0 | **采用** | 均为 npm `latest`；Router 5 在未使用 `unplugin-vue-router` 时无 breaking changes；Pinia 4 为 ESM-only，Vite 构建天然支持，只需补 `@vue/devtools-api` |

### 3.3 TypeScript 版本

| 候选 | 结论 | 理由 |
| --- | --- | --- |
| TypeScript 5.9.3 | 排除 | 保守但不符合“最新推荐版”；`@vue/tsconfig` 要求 >=5.8，5.9 可用但无必要降级 |
| TypeScript 6.0.3 | **采用** | 当前 lint 生态可用的最新稳定版；满足 `@vue/tsconfig >=5.8`、Pinia 4 `>=5.6`、`typescript-eslint <6.1.0` |
| TypeScript 7.0.2 | 不采用 | `typescript-eslint@8.72.2` 不支持；`vue-tsc@3.3.14` 与原生编译器版本的实测兼容性未证实 |

### 3.4 迁移方式

| 候选 | 结论 | 理由 |
| --- | --- | --- |
| 一次性全量替换 | 排除 | 12 个 SFC 同时改 UI、TS、主题与构建链，问题来源无法区分，回归面最大 |
| 先 TS 后 Arco | 排除 | 同一批文件要改两遍；类型错误与组件 API 错误分开暴露，但总工时更高 |
| 单页合并 + 两库并存 | **采用** | 每个页面同时完成 Arco 替换与 `lang="ts"`，改一次即可验收；迁移期包体临时增大，最后一页迁完移除 Element Plus |

### 3.5 包管理器

| 候选 | 结论 | 理由 |
| --- | --- | --- |
| bun | **采用** | 仓库已有 `web/desktop/bun.lock`；安装与脚本执行快；需在 Docker 构建中安装 bun 并固定版本 |
| pnpm | 不采用 | 与现有锁文件不一致，需要重建锁文件并改 Docker |
| yarn | 不采用 | 与现有 Docker 命令一致，但仓库没有 yarn.lock，实际未锁版本 |

### 3.6 富文本编辑器

| 候选 | 结论 | 理由 |
| --- | --- | --- |
| `@wangeditor/editor` 5.1.23 + `@wangeditor/editor-for-vue` 5.1.12 | 回退项 | 2022 年后无更新；`editor-for-vue` 的 npm `latest` 仍是 Vue 2 的 1.0.2，Vue 3 版本停在 `next` tag |
| `@wangeditor-next/editor` 6.5.1 + `@wangeditor-next/editor-for-vue` 6.5.1 | **采用（POC 门禁）** | 2026-10 更新，peer Vue `^3.0.5`，导入方式与现有 `Editor`/`Toolbar` 用法目标兼容；阶段一先做最小编辑器验证，不通过则回退并登记未完成项 |

## 4. 采用的方案与理由

采用“最新推荐版工具链 + Arco 官方 2.59.0 + TypeScript 6.0.3 + bun”的组合，按三阶段实施：

1. **阶段一：工具链与类型基础设施**。升级 Vue 3.5.45、Vite 8.3.8、Pinia 4.1.0、Router 5.5.0、ESLint 10、unplugin、vue-tsc；建立 `tsconfig.json`、`env.d.ts`、`typecheck` 脚本与 flat config；在 Element Plus 上完成构建、类型检查与页面冒烟。此阶段先验证 `vue-tsc@3.3.14 + TypeScript 6.0.3 + Vite 8` 与 `@wangeditor-next` 两个 POC。
2. **阶段二：逐页合并迁移**。按壳层与基础设施 → Login/Setup → 设置页 → ListView → EmailDetail/Editor 的顺序，每页同时替换 Arco 组件并加 `lang="ts"`；迁移期保留 Element Plus，仅新迁移页面使用 Arco。
3. **阶段三：清理与验收**。移除 `element-plus`、`@element-plus/icons-vue`、`vue-icons-plus` 和全部 `.el-*` 覆盖；关闭 `allowJs`、开启 `strict` 全量类型检查；更新功能文档、构建文档、Docker 与 `docs/README.md` 索引。

选择该组合的理由：

- 直接满足“Vue3 最新稳定版、JS→TS、Arco、相关依赖最新推荐版”的四项要求。
- TS 6.0.3 是在不牺牲 ESLint 类型规则前提下的最新可用版本；TS 7.0.2 的收益不足以抵消 lint 链不可用。
- 两库并存 + 单页合并把每次改动限制在一个页面内，便于逐页回滚与验收；最后一页迁完再删 Element Plus，避免迁移中途出现半套组件体系。
- 采用 Arco 默认视觉后，可删除大部分自定义样式覆盖，降低主题迁移成本；代价是界面观感变化，已由用户确认。

## 5. 风险与观察项

| # | 风险 | 影响 | 处置 |
| --- | --- | --- | --- |
| 1 | Arco 官方发版节奏慢于社区 fork | 后续 bug 修复等待时间不确定 | 锁定 2.59.0；验收记录版本；保留切 fork 的评估项，不在本轮引入 |
| 2 | `a-table` / `a-form` / `a-modal` API 与 Element Plus 差异大 | 28 个表格列、29 个表单项、4 个弹窗需要重写模板与校验 | 先做迁移样板页（PluginSettings），固化列配置与表单规则写法后再批量迁移 |
| 3 | Arco 默认视觉替代现有 PM 视觉 | 页面观感、间距、圆角、暗色表现变化 | 用户已确认采用 Arco 默认；验收增加逐页视觉检查；保留 `--pm-*` 仅用于布局壳层 |
| 4 | TypeScript 6.0.3 与 vue-tsc 3.3.14 的实际兼容性 | 类型检查可能报编译器内部错误或误报 | 阶段一 POC；不通过时回退 TS 5.9.3 并记录原因，不跳过类型检查 |
| 5 | Pinia 4 为 ESM-only 且需显式安装 `@vue/devtools-api` | 构建或运行时模块解析失败 | 依赖中加入 `@vue/devtools-api@8.2.1`；Vite 使用 ESM 配置 |
| 6 | Vue Router 5 的 breaking changes | 路由行为变化 | 官方迁移指南说明未使用 `unplugin-vue-router` 时无 breaking changes；阶段一验证 `createWebHistory`、`router.replace` 与 `useRoute`，并补服务端 SPA 回退 |
| 7 | Vite 8 要求 Node >=20.19 / >=22.12 | Docker 构建失败 | 本地与 Docker 统一 Node 24 |
| 8 | bun 未参与现有 Docker 构建 | 锁文件失效，安装结果不可复现 | Docker 安装 bun 并执行 `bun install --frozen-lockfile`；删除 yarn 安装步骤与残留锁文件 |
| 9 | `@wangeditor-next` 与旧版 API 不完全一致 | 编辑器页面编译或行为异常 | 阶段一最小 POC；不通过则保留旧版并登记未完成项，不阻塞其他页面 |
| 10 | 前端无自动化测试 | 组件替换后的交互回归依赖人工 | 增加 `typecheck`、`lint`、`build` 三道门禁；按页面执行登录、收信、列表、详情、发信、设置、插件审批冒烟 |
| 11 | Arco 暗色主题需 `arco-theme` 属性 | 当前依赖 `prefers-color-scheme` 的 CSS 媒体查询，切 Arco 后暗色可能不生效 | 新增系统主题监听，切换 `document.body` 的 `arco-theme`；验收覆盖浅色/深色 |

## 7. 结论

方案可行。主要成本不在“换标签”，而在 `a-table`、`a-form`、`a-modal` 的 API 重写、TypeScript 类型补齐与构建链的 Node、bun 统一。按三阶段实施，阶段一先验证两个 POC（TS 6 + vue-tsc、wangeditor-next），阶段二逐页合并迁移，阶段三清理 Element Plus 并完成类型与视觉验收。
